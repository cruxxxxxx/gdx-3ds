# 60fps-on-New3DS Research (deep-research workflow, 2026-08-14)

## Summary
Real-world precedent says a rock-solid 60fps N64 port on New 3DS is achievable but was reached by the sm64-3ds family through three levers, all directly applicable to this F-Zero X port: (1) render-side cost control — the SM64 port only held 60fps on N3DS after disabling anti-aliasing, showing PICA200 fill/resolve cost, not game logic, was the blocker; (2) aggressive CPU distribution — 804MHz+L2 via osSetSpeedupEnable, the audio thread moved to N3DS core 2 (freely usable for homebrew under Luma; core 3 is off-limits due to QTM), and a speed-over-accuracy RSP audio HLE path enabled by default; (3) frame pacing via C3D_FrameRate(60) combined with 30Hz game logic plus a second per-tick render pass that patches interpolated values into the retained display list. The shipped 3DS compiler baseline (-march=armv6k -mtune=mpcore -mfloat-abi=hard -ffast-math -fomit-frame-pointer) confirms hard-float VFP + fast-math is the proven float-physics configuration on this GCC/devkitARM target. On audio, the stock DSP firmware exposes 24 individually configurable voices with per-voice DSP-side resampling (ndspChnSetRate + polyphase/linear interpolation), so N64 HLE resampling and final mixing can be offloaded from the ARM11, and a Teak C/C++ toolchain (Gericom's teak-llvm) exists for going beyond ndsp. Notably, F-Zero X natively runs 60Hz logic, unlike SM64's 30Hz-plus-interpolation approach, so its CPU budget per frame is tighter than the precedent — making the multi-core split and the AA/fill-rate lesson the highest-leverage findings.

Luma v10.1.1 changelog confirms the 3DSX core1 limit increase.

### N3DS core 2 is freely usable by homebrew under Luma3DS: Luma automatically injects the core2 kernel capability
- confidence: high | vote: 3-0 (two merged claims, unanimous)
- claim: N3DS core 2 is freely usable by homebrew under Luma3DS: Luma automatically injects the core2 kernel capability (exheader kernel-flags bit 0x2000, descriptor 0xFF002109) into every 3dsx process at creation, so no extra patch or config is needed to threadCreate on core 2. On stock kernels, core-2 thread creation from a non-BASE process requires that 0x2000 exheader flag, and core 3 is unconditionally denied to non-BASE processes — so core 2 is homebrew's extra N3DS core.
- evidence: TuxSH (Luma maintainer): "Core2 access is granted via a kernel capability, which we automatically grant to all 3dsx apps... Yes, it sets it when creating a process." Verified in Luma master: sysmodules/loader/source/hbldr.c injects 0xFF002109 ('Access core2'). 3dbrew: "When processorid==0x2 and the process is not a BASE mem-region process, exheader kernel-flags bitmask 0x2000 must be set (otherwise error 0xD9001BEA)"; processorid==0x3 from non-BASE always errors. Note: injected caps default affinity to core 0, so threads must explicitly pass core id 2 to threadCreate.
- sources: https://github.com/LumaTeam/Luma3DS/pull/1668, https://www.3dbrew.org/wiki/Multi-threading

### Do not plan around core 3: even when thread creation is unlocked, QTM (head-tracking) runs at very high priori
- confidence: high | vote: 3-0
- claim: Do not plan around core 3: even when thread creation is unlocked, QTM (head-tracking) runs at very high priority on core 3 and the N3DS GPU driver depends on QTM, so app threads there get starved. Luma's lead developer states user applications are not meant to use core 3 at all and should use core 2 instead.
- evidence: TuxSH: "This is not something you can fix, QTM is running at very high priority on core3, and the GPU driver depends on QTM on N3DS. User applications are not meant to use core3 at all. Just use core2 instead." His empirical test pinning threads to core 3 "often resulted in one or multiple threads being starved." Corroborated by 3dbrew (QTM handler on core2-3) and Copetti's 3DS analysis.
- sources: https://github.com/LumaTeam/Luma3DS/pull/1668, https://www.3dbrew.org/wiki/HID_Services

### Core 1 (syscore) is usable but rationed: apps cannot run threads on core 1 by default and must first call APT:
- confidence: high | vote: 3-0
- claim: Core 1 (syscore) is usable but rationed: apps cannot run threads on core 1 by default and must first call APT:SetApplicationCpuTimeLimit to reserve a percentage (valid 5-89%) of syscore time; e.g. 25% caps the app at 25% of core 1. libctru allows only a single app thread on core 1. Relevant if the port wants a fourth lane (e.g. low-rate background work) beyond cores 0 and 2 on N3DS.
- evidence: 3dbrew: "You are not able to use the system core (core1) by default... if you set this value to 25%, it means that your application will be able to use 25% of the system core at most." libctru docs: "Processor #1 is the system core. If APT_SetAppCpuTimeLimit is used, it is possible to create a single thread on this core." Caveat: limit cannot be reset to 0% once set.
- sources: https://www.3dbrew.org/wiki/Multi-threading, https://libctru.devkitpro.org/thread_8h.html

### The 3DS scheduler is strictly priority-preemptive with NO timeslicing: a thread that never blocks or yields st
- confidence: high | vote: 3-0
- claim: The 3DS scheduler is strictly priority-preemptive with NO timeslicing: a thread that never blocks or yields starves all equal- and lower-priority threads on its core. Any worker-thread design for this port (audio, swizzle, command generation) must block on events/sleep rather than busy-wait, and the cooperative-fiber N64 scheduler must yield to the kernel where cross-thread signaling is needed.
- evidence: 3dbrew: "no timeslice-based scheduling is performed... if a thread uses up all available CPU time... all other threads with equal or lower priority that run on the same CPU core won't get a chance to run." Subv's kernel RE (used by Citra) corroborates: rescheduling only at SVCs/interrupts/timeouts.
- sources: https://www.3dbrew.org/wiki/Multi-threading, https://gist.github.com/Subv (3DS kernel scheduler findings)

## Caveats
1) Coverage gaps: NO claims survived on PICA200/citro3d GPU profiling specifics (GPUREG timers, gspWaitForP3D timing, C3D_GetProcessingTime/C3D_GetDrawingTime usage), draw-call batching costs, texture-upload minimization patterns, VBO strategies, or fragment-lighting vs texenv costs — items (3) and much of (6) of the research question are answered only indirectly via the AA fill-rate finding. Zelda OoT 3DS decomp-port evidence also did not survive. 2) Two claims about the SM64 port's frame-pacing internals were REFUTED in verification (the ENABLE_N3DS_FRAMESKIP '30fps target' framing, and the 'extra gspWaitForVBlank gated on C3D_GetProcessingTime' pattern) — do not rely on those mechanisms as described; the verified pacing mechanism is C3D_FrameRate(). 3) No surviving claim contains measured numbers (ms/frame, percent gains) for any optimization — the RSPA 'measurable cost' finding rests on engineering-effort inference, and no LTO/-O3-vs-O2 benchmarks exist in the record. 4) Time sensitivity: the AA/60fps test data is from Aug 2020 builds ('brief testing', minor level-load slowdowns admitted); later Wyatt-James builds are further optimized, so the AA ceiling may have moved, though the fill-rate lesson stands. Luma details verified against 2022-2026 sources and current master; 3DS kernel/QTM behavior is frozen so those findings do not decay. 5) Transferability: SM64's 60fps is 30Hz logic + interpolation; F-Zero X natively runs 60Hz logic with 30-machine physics, so the SM64 precedent bounds render-side feasibility but NOT the CPU budget for true 60Hz simulation — the port's headroom there is unproven by any source in this record.
