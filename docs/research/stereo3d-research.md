# Stereoscopic 3D Research (deep-research workflow, 2026-08-14)

## Summary
High-quality stereo on 3DS/citro3d follows a well-documented canonical pattern: enable gfxSet3D(true) (off by default), create two 240x400 color+depth render targets bound to GFX_TOP/GFX_LEFT and GFX_RIGHT, and inside one C3D_FrameBegin/FrameEnd render the full scene twice, switching with C3D_FrameDrawOn and skipping the right-eye pass when the slider reads zero — stereo therefore roughly doubles vertex and fragment work, with no PICA multiview sharing, and it is hardware-mutually-exclusive with 800px wide mode. For projection math, citro3d's Mtx_PerspStereoTilt provides correct off-axis asymmetric-frustum stereo (shear = iod/(2*screen) plus an iod/2 translation, ±iod per eye, 'screen' = zero-parallax convergence plane), which industry sources (NVIDIA GDC 2011) confirm is the correct approach versus toe-in rotation; the equivalent clip-space-X-shift trick shows a shear can validly be applied at the final transform stage even when the backend only sees the game's pre-multiplied CPU-side matrices. The sm64-3ds port (mkst/Wyatt-James gfx_citro3d.c — the direct ancestor of this backend's stubs) took exactly that shortcut: stereoTilt() uploads an identity matrix with gSliderLevel/iodZ and gSliderLevel/iodW written into r[1].z/r[1].w (defaults 8/16) atop the game's baked mv*p, redrawing each vertex buffer per eye — but its own author flags this as a workaround, with a TODO to move stereo into gfx_pc before the mv*p multiply for 'proper and portable' support (the commented-out proper version kills z-buffer, clipping, and fog). Framebuffer-effect problems were solved with explicit per-drawcall tagging (s2DMode 0-4: identity projection for pure 2D at zero parallax, clamped divisors for semi-3D UI, skip for the score menu) inserted manually into game code via a G_SPECIAL_1 gbi command, and the ortho skybox artifact (popping out at HUD depth) was fixed by pushing the skybox plane deeper than all 3D geometry rather than touching the projection. Comfort guidance: parallax at infinity equals eye separation, never force divergence, close-screen viewers tolerate at most ~50% of real 6.5 cm IPD, and separation must remain user-adjustable — which the 3DS slider (osGet3DSliderState, 0-1, linearly scaled in official examples) provides per frame.

### citro3d ships correct off-axis stereo projection math: Mtx_PerspStereoTilt(fovy, aspect, near, far, iod, scree
- confidence: high | vote: 3-0, 3-0, 3-0, 3-0 (merged claims 2, 4, 5, 6)
- claim: citro3d ships correct off-axis stereo projection math: Mtx_PerspStereoTilt(fovy, aspect, near, far, iod, screen, isLeftHanded) builds a parallel-axis asymmetric frustum via a depth-dependent shear (shift = iod/(2*screen)) plus an eye-offset translation (iod/2) baked into the projection — not a toe-in rotation. Pass -iod for the left eye and +iod for the right from one shared camera parameter set. The 'screen' parameter is the zero-parallax convergence plane: geometry beyond it recedes into the display, geometry nearer pops out, geometry at exactly 'screen' sits at the display surface — the knob for placing HUD elements at screen depth. The Tilt variant additionally accounts for the 3DS's 90-degree-rotated framebuffer (which is why the shear lands in row 1, not row 0).
- evidence: mtx_perspstereotilt.c: "float shift = iod / (2.0f*screen);" ... "mtx->r[1].w = iod / 2.0f;" ... "mtx->r[1].z = -mtx->r[3].z * shift / fovx_tan_invaspect;" with comment "With stereo, left/right separation becomes top/bottom separation." maths.h doc: "Plug in -iod for the left eye and iod for the right eye"; "If objects are further than this [screen], they will appear to be inside the screen... Objects at this distance appear to be at the screen." composite_scene uses it with screen=2.0f and iod=slider/3.
- sources: https://github.com/devkitPro/citro3d/blob/master/source/maths/mtx_perspstereotilt.c, https://github.com/devkitPro/citro3d/blob/master/include/c3d/maths.h, https://github.com/devkitPro/3ds-examples/blob/master/graphics/gpu/composite_scene/source/main.c

### Off-axis (parallel, sheared) projection is validated as the correct stereo technique by industry sources: toed
- confidence: high | vote: 3-0, 3-0 (merged claims 19, 20)
- claim: Off-axis (parallel, sheared) projection is validated as the correct stereo technique by industry sources: toed-in cameras introduce vertical/keystone deformation because image planes are not parallel to the screen and cannot be fully corrected. Crucially for a backend that only sees the game's final CPU-computed matrices: the stereo projection is just a horizontally offset mono projection, equivalently implementable as a clip-space X shift at the end of the vertex shader (SV_Position.x += parallax when w != 1) — the exact technique NVIDIA's 3D Vision driver applies automatically to games with zero source access. This legitimizes applying the shear at the backend on the final matrix stage for the F-Zero X port, provided the caveats about depth/fog interaction are handled.
- evidence: GDC 2011 (Gateau/NVIDIA + Filion/Blizzard, StarCraft 2): "Projection Direction is parallel to mono direction (NOT toed in)... Toed in frustum introduces deformation which is really painful"; "Stereo projection matrix is a horizontally offset version of regular mono projection matrix"; "Just before rasterization in the vertex shader, offset the clip position by the parallax amount... Shift SV_Position.x... if SV_Position.w != 1". 3D Vision docs: driver applies PsInput.x += Separation*(PsInput.w - Convergence) via automatic vertex-shader patching with per-eye drawcall duplication. Corroborated by Woods et al. 1993 on keystone distortion from toe-in.
- sources: https://www.nvidia.com/content/pdf/gdc2011/stereoscopy.pdf, https://archive.docs.nvidia.com/gameworks/content/technologies/desktop/nv3dva_background.htm

### HUD/2D wrong-depth problems are solved with an explicit per-drawcall class enum (s2DMode), NOT automatic ortho
- confidence: high | vote: 3-0, 3-0 (merged claims 12, 16 — semantic duplicates; note a stricter '2-triangle heuristic' variant was REFUTED 0-3)
- claim: HUD/2D wrong-depth problems are solved with an explicit per-drawcall class enum (s2DMode), NOT automatic ortho-matrix detection: mode 0 = 3D (full stereo tilt); mode 1 = 'pure 2D' uploads an identity tilt matrix and returns early, landing those draws at zero parallax (screen depth); modes 2 and 3 (Goddard hand/'press start' text, credits) clamp the stereo divisors to fixed constants (±32.0f, ±64.0f) to reduce but not remove parallax; mode 4 (score menu) skips the matrix upload entirely. - evidence: stereoTilt lines 160-174: "case 1 : // pure 2D — C3D_FVUnifMtx4x4(...); return; case 2 : // goddard hand and press start text — z = (z < 0) ? -32.0f : 32.0f; ... case 3 : // credits — ±64.0f; case 4 : // the goddamn score menu — return;". gbi.h line 4802 defines gDPSet2d via G_SPECIAL_1; gfx_pc.c line 1638 dispatches it under #ifdef TARGET_N3DS. ## Caveats
1) Performance data gap: no surviving claim contains a measured fps cost of stereo on New3DS hardware (for sm64-3ds or any citro3d homebrew) — the ~2x vertex/fragment cost is inferred from code structure (two full passes, no PICA multiview), not benchmarked; the actual hit for a CPU-bound game may be much smaller than 2x wall-time since GPU work overlaps CPU frames. Bandwidth comparison between 800px-wide transfers and 2x240x400 stereo transfers was not quantified. 2) Three claims were refuted in verification and should not be relied on: the second eye pass does re-copy vertex data CPU-side (not upload-free); sm64-3ds uses its hand-rolled shear, not Mtx_PerspStereoTilt; and 2D classification is purely the manual s2DMode tag, with no 2-triangle heuristic. 3) Questions (3) and (5) of the brief are only partially answered: fog, decals, and mirror/transition-capture behavior in stereo were not directly evidenced (only the author's 'kills fog/zbuffer/clipping' annotations on the post-mv*p approach, and the skybox case study); Nintendo's official health/safety conventions, slider response curve, and saved-setting guidance come from confidential SDK documentation and were not sourced — only the homebrew-side linear-slider pattern is confirmed. 4) The sm64-3ds code is from 2020; it is cited as a historical design precedent (which is stable), but the Wyatt-James fork has ongoing development and later revisions may differ from the lines verified here. 5) The devkitPro example verified is composite_scene; the brief's named 'stereoscopic_3d' example does not exist under that name in the repo (stereoscopic_2d and wide_mode_3d do).
