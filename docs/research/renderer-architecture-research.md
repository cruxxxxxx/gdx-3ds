# Renderer Architecture Research: N64->PC decomp graphics submission (2026-08-15)

## Summary
The libultraship Fast3D interpreter your F-Zero X 3DS port uses is the mainstream, well-trodden choice for constrained-hardware N64 ports, and the evidence does not point to a faster drop-in submission architecture for the PICA200. The two architectural families are (a) HLE display-list interpreters (Emill's n64-fast3d-engine / libultraship's gfx_pc), which walk the F3DEX2 command buffer each frame on the CPU and hand pre-converted, batched triangles to a swappable per-platform GPU backend, and (b) RT64 (used by N64Recomp/Zelda64Recomp), a fundamentally different deferred renderer that logs an entire frame's draw history, offloads RSP vertex transform to a GPU compute shader, and targets only modern APIs (D3D12/Vulkan/Metal, Shader Model 6). RT64 is architecturally superior for CPU offload but is categorically unavailable on the 3DS: the PICA200 is a 2006-era fixed-function GPU with no compute shaders and none of the required modern-API feature levels, so RT64 cannot be a target. Every successful constrained-hardware port examined — the SoH Wii U port (native GX2 backend), the SM64 3DS ports (citro3d/PICA200 backend), and the native decomp PC ports (Perfect Dark, mgb64, GoldenEye) — kept the Fast3D display-list interpreter and only retargeted the leaf GPU backend; none abandoned the interpreter or bypassed the GBI layer to emit native draw calls from decompiled draw functions. The strongest caveat is that the corpus contains almost no direct profiling data quantifying Fast3D's per-command CPU cost on 3DS versus GPU/driver cost, so whether the interpreter is your actual 60fps bottleneck remains empirically unproven from these sources.

## Findings
### RT64 uses a fundamentally different submission model from Fast3D: it defers all draw calls into a whole-frame 
- confidence: high | vote: 3-0 (all constituent claims unanimous)
- claim: RT64 uses a fundamentally different submission model from Fast3D: it defers all draw calls into a whole-frame auxiliary history structure, offloads RSP vertex transform (position/lighting/texturing) to a GPU compute shader, defers memory/texture reads until full RDP sync, and uses ubershaders to avoid pipeline-compilation stutter — whereas Fast3D interprets each display-list command on the CPU inline per-frame.
- evidence: RT64 README verbatim: 'Draw calls are never sent right away to the GPU but instead stored on an auxiliary structure that logs the history of an entire frame'; 'All vertex transformations by the RSP (e.g. position, lighting, texturing, etc.) are performed by a highly parallel compute shader in the GPU' (saving CPU time, enabling higher poly counts); 'Any operation related to reading memory and using it as texture information during rendering is completely deferred until the game requires a full synchronization of the RDP'; 'Uses ubershaders to guarantee no stutters due to pipeline compilation.' Fast3D by contrast (Emill gfx_pc.c gfx_run/gfx_run_dl) does RSP vertex transform, lighting, and clipping on the host CPU inline as it walks the F3DEX2 buffer. Merges verified claims [0][1][2][3][20][21].
- sources: https://github.com/rt64/rt64/blob/main/README.md, https://github.com/Zelda64Recomp/Zelda64Recomp

- confidence: high | vote: 3-0
- claim: The 3DS citro3d/PICA200 backend already implements draw-call batching: it accumulates Fast3D's pre-converted vertex/triangle data (not raw GBI microcode) into a single 1MB VBO tracked by sBufIdx and flushes multi-triangle batches with C3D_DrawArrays(GPU_TRIANGLES, ...), rather than one GPU draw per Fast3D triangle command.
- evidence: gfx_citro3d.c: sVboBuffer = linearAlloc(1*1024*1024) ('Create 1MB VBO'); geometry written at &((float*)sVboBuffer)[sBufIdx * VERTEX_SHADER_SIZE]; drawn via C3D_DrawArrays(GPU_TRIANGLES, sBufIdx, buf_vbo_num_tris*3); then sBufIdx += buf_vbo_num_tris*3 (reset per frame). Upstream gfx_pc.c accumulates up to MAX_BUFFERED (256) same-state triangles into buf_vbo before calling gfx_rapi->draw_triangles, so each C3D_DrawArrays covers a multi-triangle batch. The citro3d backend receives already-formatted VBO data (position/texcoord/color/fog) and does not parse microcode. Merges verified claims [8][9][11].
- sources: https://github.com/mkst/sm64-port/blob/3ds-port/src/pc/gfx/gfx_citro3d.c, https://github.com/Wyatt-James/sm64-3ds-port

### The N64's original hardware pipeline is why the display-list-interpretation cost exists on modern targets: the
- confidence: high | vote: 3-0
- claim: The N64's original hardware pipeline is why the display-list-interpretation cost exists on modern targets: the game uploaded per-frame display lists of opcodes that RSP microcode (F3DEX2) interpreted for transform/lighting, then handed triangles to the fixed-function RDP for rasterization/blending. Fast3D moves the RSP-interpretation step onto the host CPU; RT64 moves it onto a GPU compute shader.

This is the work that the real N64's RCP did in hardware and that Fast3D now does on CPU (the premise of the research question) — RT64's compute-shader approach is the architectural answer to reclaiming that offload, but requires a programmable GPU the PICA200 lacks. ## Caveats
MAJOR EVIDENCE GAP: The verified corpus contains essentially NO direct profiling data quantifying Fast3D's per-command display-list interpretation CPU cost versus GPU/driver cost on the 3DS (or any platform). The research question's core sub-question (2) — 'is Fast3D's per-frame interpretation actually a meaningful CPU bottleneck in practice' — was NOT answered with hard numbers; no GitHub issue, flamegraph, or developer statement quantifying the CPU split survived verification. Any claim that Fast3D IS or IS NOT your 60fps bottleneck on New3DS is currently unsupported by this evidence and must be resolved by profiling the actual port. Similarly, sub-question (3) — specific measured optimizations to Fast3D-family interpreters (display-list memoization/caching of unchanged lists, vertex/matrix caching, state-change reduction) implemented and MEASURED in libultraship/SoH forks — produced no verified concrete-benchmark claims; only the always-present draw-call batching (1MB VBO / C3D_DrawArrays) was confirmed in code, not measured. DaedalusX64's 20-30fps figure is secondary (wiki/forum) and, per the verifier's own note, is a weak analogy because it measures full emulation, not the decomp+Fast3D path. Two citations in the source set attributed RT64 README text to the Zelda64Recomp repo (RT64 is the true origin, pulled in as the renderer); this is citation imprecision, not a factual error. Time-sensitivity: RT64 and the Recomp projects are actively developed (2024-2026); RT64's API/feature requirements could theoretically change, but a compute-shader deferred renderer will not become PICA200-compatible.

## Open questions
- What is the actual CPU-vs-GPU time split in the F-Zero X 3DS port right now? Only direct profiling (e.g. citra/hardware timing of gfx_run_dl interpretation vs C3D_DrawArrays/GPU submit) can determine whether Fast3D interpretation is the real 60fps bottleneck — the literature does not answer this.
- Has anyone implemented and MEASURED display-list caching/memoization (skipping re-interpretation of unchanged static lists) or vertex/matrix result caching in a libultraship/Fast3D fork? F-Zero X has largely static track/vehicle geometry per frame, so this could be high-value, but no verified prior art or benchmark was found.
- Given F-Zero X specifically (native ARM game logic already fast), would a targeted hybrid — precompiling/caching the port's known-static display lists into ready-to-submit PICA200 VBOs while keeping Fast3D for dynamic lists — beat pure per-frame interpretation, and what is the memory budget on New3DS for such caches?
- Are there 3DS-specific PICA200 bottlenecks (fixed-function pipeline stalls, texture upload cost, GPU_TRIANGLES fill rate) that dominate over the interpreter, meaning renderer-submission changes would not move the framerate at all?
