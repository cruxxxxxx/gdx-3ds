# Deep research 2: what's left for a locked 60 on New 3DS (2026-09-03)

Adversarially verified (3-voter) findings; 100 agents. Question: multi-core, interpreter
micro-architecture, PICA200 batching, stereo cost, 30 Hz+interp.

## Summary
On New 3DS the only extra core an application can realistically use is core 2: Luma automatically grants the 0x2000 kernel capability to 3dsx homebrew, core 3 is blocked by the stock kernel and starved by QTM/GSP even when patched in, and core 1 (syscore) is available only fractionally via APT_SetAppCpuTimeLimit. The best-documented N64 precedent (the sm64 3DS port, Wyatt-James/mkst/Gericom lineage) offloads only audio to core 2 and keeps game logic, display-list interpretation and citro3d draws on core 0; no verified precedent pipelines rendering across cores, and its 60 fps enhancement re-runs the whole interpreter twice per 30 Hz logic tick with midpoint interpolation, doubling dispatch cost rather than hiding it. On the interpreter side, ARM11 never predicts register-indirect branches (BX reg / LDR pc / ADD pc cost 5-9 cycles each regardless of dispatch style), so computed-goto vs switch buys only a few cycles per command; the Haswell "prediction no longer matters" result does not transfer. citro3d's cost model shows state changes are lazy dirty-bits, a texenv rebind is a single 5-word write and C3D_DrawArrays is 11 register appends, so the ~22 us/draw the port measures comes from the batch split (UpdateContext binds, wrapper, buffer handling), not the raw register writes — which makes reducing batch breaks (folding prim/env colors into the texenv constant or a per-vertex attribute, collapsing SETTILE churn) the highest-value target, followed by moving the bridge pre-pass / vertex packing to core 2, then fixing stereo so the right eye reuses packed vertices instead of repacking as sm64 does.

## Findings

### 1. [high] Core availability under libctru/Luma: core 2 is usable by application threads on New 3DS — the stock kernel requires exheader kernel-flags bit 0x2000 (else svcC...

Core availability under libctru/Luma: core 2 is usable by application threads on New 3DS — the stock kernel requires exheader kernel-flags bit 0x2000 (else svcCreateThread returns 0xD9001BEA), and Luma3DS's hbldr sets it automatically (descriptor 0xFF002109) for every .3dsx, so no user patch is needed. Core 3 is refused by the stock kernel for non-BASE processes, and even with Luma's optional kernel patch it is unusable in practice because QTM runs many very-high-priority threads there and GSP depends on QTM, causing starvation/deadlock for anything that touches the GPU; the Luma maintainer's guidance is 'use core 2, it is by default completely idle'. Core 1 (syscore) is reachable only via APT_SetAppCpuTimeLimit; Luma's hbldr sets the reslimit to BIT(7)|89 (up to 89%), while the sm64 port documents and uses a 10-80% range.

Evidence: TuxSH (Luma maintainer) on PR 1668: 'Core2 access is granted via a kernel capability, which we automatically grant to all 3dsx apps ... Yes, it sets it when creating a process' and 'QTM is running at very high priority on core3, and the GPU driver depends on QTM on N3DS. User applications are not meant to use core3 at all. Just use core2 instead.' libctru thread.h: 'Processor #2 ... Normal applications can create threads on this core if the exheader kernel flags bitmask has 0x2000 set. Processor #3 ... Normal applications cannot create threads on this core. Processes in the BASE memory region can always create threads on processors #2 and #3.' 3dbrew confirms the kernel checks and the 0xD9001BEA error; 3dbrew notes the scheduler is strict priority-preemptive with no timeslicing, so QTM threads fully starve lower-priority app threads on the same core. Luma hbldr.c line 193: '0xFF002109, // Exflags: APPLICATION memtype + Shared page writing + Allow debug + Access core2' and reslimits[0] = BIT(7)|89.

Sources: https://github.com/LumaTeam/Luma3DS/pull/1668, https://libctru.devkitpro.org/thread_8h.html, 3dbrew Multi-threading page (svcCreateThread processorid checks), Luma3DS sysmodules/loader/source/hbldr.c (kernel capability table), Luma3DS commit fcd08d6 (Patch kernel11 to remove checks on core2/3 thread creation)

### 2. [high] Precedent for multi-core N64 ports: the sm64 3DS port (Wyatt-James / mkst 3ds-port lineage) offloads only RSP audio synthesis to another core — core 2 on New 3D...

Precedent for multi-core N64 ports: the sm64 3DS port (Wyatt-James / mkst 3ds-port lineage) offloads only RSP audio synthesis to another core — core 2 on New 3DS, core 1 on Old 3DS after a successful APT_SetAppCpuTimeLimit(80) (needs Luma >= 10.1.1), with a fallback to running audio on the main thread (Thread5) if that or threadCreate fails. The audio thread is created with threadCreate(..., 64 KiB stack, priority 0x18, core id, detached) and the main thread is set to 0x19 via svcSetThreadPriority. Game logic, display-list interpretation (gfx_run) and citro3d submission all stay synchronous on the main thread/core 0. Among verified sources there is no N64 port that pipelines game logic and rendering across cores with measured gains.

Evidence: audio_3ds.c:216-224: 'if (is_new_n3ds()) { s_audio_cpu = NEW_CORE_2; } else if (R_SUCCEEDED(APT_SetAppCpuTimeLimit(N3DS_AUDIO_CORE_1_LIMIT))) { s_audio_cpu = OLD_CORE_1; } else { s_audio_cpu = OLD_CORE_0; // Run in Thread5 }'; line 232: threadCreate(audio_3ds_loop, NULL, 64*1024, 0x18, s_audio_cpu, true); threadId==NULL sets s_thread5_does_audio. audio_3ds_threading.h: MAIN_THREAD 0x19, AUDIO_THREAD 0x18, CORE_1_LIMIT 80 ('Can be [10-80]'), IDLE 10. Repo-wide grep finds exactly one threadCreate; pc_main.c calls thread5_game_loop synchronously and send_display_list() is 'gfx_run(...)' on the main thread. README: 'Multi-threaded; audio thread runs on Core 1 on O3DS and Core 2 on N3DS; needs Luma v10.1.1 or higher'. Verifier note: on New 3DS the port never calls APT_SetAppCpuTimeLimit at all. Implication for this port: ndsp audio already occupies core 2, so a render/bridge thread on core 2 must be prioritized against ndsp threads under the no-timeslice scheduler.

Sources: https://github.com/Wyatt-James/sm64-3ds-port (src/pc/audio/audio_3ds.c, audio_3ds_threading.h, src/pc/gfx/gfx_3ds.c, README), https://github.com/Wyatt-James/sm64-3ds-port/blob/3ds-port/src/pc/audio/audio_3ds.c

### 3. [high] Stereo 3D in the sm64 3DS port (both Wyatt-James and mkst branches) is brute force: every triangle batch is submitted twice — stereoTilt() shears the projection...

Stereo 3D in the sm64 3DS port (both Wyatt-James and mkst branches) is brute force: every triangle batch is submitted twice — stereoTilt() shears the projection matrix and re-uploads it as a vertex uniform, gfx_citro3d_frame_draw_on() re-sets framebuffer/viewport/scissor to the right-eye target, the VBO write index is rewound, and gfx_citro3d_draw_triangles() is called again, which re-executes the entire CPU vertex repack loop (position copy, UV scale/flip, color fill; the two-color path even re-runs the constancy scan and update_shader). So CPU stereo cost is ~2x vertex emission plus 2x draw/state work, not merely 2x DrawArrays. There is no single-pass, command-list-reuse, or geometry-shader trick, and enabling 3D forces 400px width with AA/wide disabled.

Evidence: gfx_citro3d_draw_triangles_helper: 'sOrigBufIdx = sBufIdx; stereoTilt(&projection, -iodZ, -iodW); gfx_citro3d_frame_draw_on(gTarget); gfx_citro3d_draw_triangles(...); sBufIdx = sOrigBufIdx; stereoTilt(&projection, iodZ, iodW); gfx_citro3d_frame_draw_on(gTargetRight); gfx_citro3d_draw_triangles(...)'. gfx_citro3d_draw_triangles (743-799) contains the full per-vertex repack loop ending in C3D_DrawArrays(GPU_TRIANGLES, sBufIdx, n*3). stereoTilt ends with C3D_FVUnifMtx4x4(GPU_VERTEX_SHADER, uLoc_projection, mtx). Only one shader binary exists; grep for geometry shader/instancing/command-list reuse returns nothing. gfx_3ds_update_stereoscopy sets useAA=false, useWide=false when slider>0; width = (useAA||useWide) ? 800 : 400. A competing claim that stereo 'does not duplicate vertex packing' was refuted 0-3. For this port the actionable lesson is the opposite of the precedent: pack once and issue a second C3D_DrawArrays over the same VBO range after swapping only the projection uniform and framebuffer, which removes the duplicate per-triangle cost (a large share of the 4.6 ms per-triangle path if this port currently mirrors the sm64 design).

Sources: https://github.com/Wyatt-James/sm64-3ds-port (src/pc/gfx/gfx_citro3d.c lines 810-826, gfx_3ds.c 111-175), https://github.com/mkst/sm64-port/blob/3ds-port/src/pc/gfx/gfx_citro3d.c

### 4. [high] ARM11 branch prediction (ARM1176JZF-S TRM; identical wording in the ARM11 MPCore TRM used by the 3DS): the dynamic predictor is a 128-entry direct-mapped BTAC i...

ARM11 branch prediction (ARM1176JZF-S TRM; identical wording in the ARM11 MPCore TRM used by the 3DS): the dynamic predictor is a 128-entry direct-mapped BTAC indexed by VA[9:3] with 2-bit saturating counters, predicting only constant-offset branches (0 cycles folded, 1 cycle otherwise). Static prediction is backward-taken/forward-not-taken: 1 cycle correct not-taken, 4 cycles correct taken, 5-7 cycles mispredicted (Cycle = MAX(MaxCycles - FlagCycleDistance, MinCycles)). Register-indirect branches are never predicted (except return-shaped forms via a 3-entry return stack): BX reg 5-7 cycles, MOV pc 5, ADD pc,Rd,Rm 7, LDR pc from table 8-9. Consequence for the display-list interpreter: switch (LDR pc jump table) and computed-goto (LDR + BX/MOV pc) dispatch both pay a ~5-9 cycle unpredicted jump per command; threaded dispatch saves only the bounds check and loop-back branch, a few cycles per command, and the Intel/ITTAGE result that indirect prediction 'no longer matters' does not transfer to ARM11.

Evidence: TRM: 'The dynamic branch predictor is a 128-entry direct-mapped branch predictor using VA bits [9:3] ... Only branches with a constant offset are predicted. Branches with a register-based offset are not predicted ... A dynamically predicted branch takes one cycle or zero cycles if folded out.' Table 16-11: 'B<immed> ... 1 Correct not-taken static prediction; 4 Correct taken static prediction; 5-7 Incorrect dynamic/static prediction; BX <cond> <reg> 5-7 If taken'; data-processing/load tables: 'MOV pc, <Rd> 5; ADD pc, <Rd>, <Rm> 7; LDR pc, <addr_md_1cycle> 8; LDR pc, <addr_md_2cycle> 9'. Footnote: 'Mispredicted branches, including taken unpredicted branches, takes a varying number of cycles ... Cycle = MAX(MaxCycles - FlagCycleDistance, MinCycles)'. Return stack predicts BX lr / MOV pc,lr / LDMIA sp!,{..,pc} (4 cycles correct, 7 mispredicted). CGO 2015 abstract: 'Using both hardware counters on Haswell ... and simulation of the ITTAGE, we show that the accuracy of indirect branch prediction is no longer critical for interpreters' — scoped to modern Intel predictors; a claim extrapolating it to ARM11 was voted down 1-2 and the paper has no ARM11 data. Magnitude check: 7.8 ms of dispatch remainder is ~6.3M cycles at 804 MHz; unless the command count is in the tens of thousands per frame, the ~5-9 cycles of indirect jump per command is a small fraction — the cost is inside the handlers (SETTILE, batch-breaking state changes, texrects), so dispatch-style changes are a sub-millisecond lever.

Sources: https://developer.arm.com/documentation/ddi0301/h/program-flow-prediction/branch-prediction (ARM DDI 0301H sections 5.2, 16.1, Table 16-11), ARM11 MPCore TRM ARM DDI 0360F section 15.1, https://core.ac.uk/outputs/228060502/ (Rohou, Swamy, Seznec, CGO 2015)

### 5. [high] citro3d/PICA200 batching cost model: state setters (C3D_SetTexEnv, C3D_TexBind, C3D_SetBufInfo, viewport/scissor) only set dirty bits and copy a small struct; r...

citro3d/PICA200 batching cost model: state setters (C3D_SetTexEnv, C3D_TexBind, C3D_SetBufInfo, viewport/scissor) only set dirty bits and copy a small struct; register emission is deferred to C3Di_UpdateContext() at the next C3D_DrawArrays, so redundant state churn between draws costs only flag writes, but every distinct state change followed by a draw forces a batch split. A texenv stage rebind (how a combiner or prim/env constant color change is expressed) is one GPUCMD_AddIncrementalWrites of 5 words (source, operand, combiner, color, scale). C3D_DrawArrays itself is exactly 11 GPU register appends regardless of triangle count. citro3d never compares old vs new values, and a texture rebind additionally rewrites TEXUNIT_CONFIG with a texture-cache clear. Therefore the ~22 us/draw this port measures (1.2 ms / ~55 draws) cannot be the register writes; it is the port's DrawTriangles wrapper, UpdateContext binds triggered by the state change, and vertex-buffer handling — i.e. the cost of a batch break is the split, so reducing the ~30 prim/env-color-induced breaks and ~130 SETTILEs is the lever.

Evidence: drawArrays.c: after C3Di_UpdateContext(), exactly PRIMITIVE_CONFIG, RESTART_PRIMITIVE, INDEXBUFFER_CONFIG=0x80000000, NUMVERTICES, VERTEX_OFFSET, GEOSTAGE_CONFIG2, START_DRAW_FUNC0, DRAWARRAYS, START_DRAW_FUNC0, GEOSTAGE_CONFIG2, VTX_FUNC (11 writes, last content change 2016). texenv.c: 'void C3Di_TexEnvBind(int id, C3D_TexEnv* env) { if (id >= 4) id += 2; GPUCMD_AddIncrementalWrites(GPUREG_TEXENV0_SOURCE + id*8, (u32*)env, sizeof(C3D_TexEnv)/sizeof(u32)); }' with sizeof(C3D_TexEnv)=20 bytes. C3D_SetTexEnv: 'ctx->flags |= C3DiF_TexEnv(id); if (env) memcpy(...)'; C3D_TexBind: 'ctx->flags |= C3DiF_Tex(unitId); ctx->tex[unitId] = tex;'. base.c UpdateContext: 'if (ctx->flags & C3DiF_TexEnvAll) { for (i = 0; i < 6; i ++) { if (!(ctx->flags & C3DiF_TexEnv(i))) continue; C3Di_TexEnvBind(i, &ctx->texEnv[i]); } ... }'. No source quantifies PICA200 stall behavior on mid-frame texenv changes or gives hardware per-draw timings.

Sources: https://github.com/devkitPro/citro3d/blob/master/source/drawArrays.c, citro3d source/base.c (C3Di_UpdateContext), source/texenv.c (C3Di_TexEnvBind), source/texture.c, include/c3d/texenv.h

### 6. [high] Folding N64 prim/env colors: the sm64 3DS port folds constant combiner colors into the PICA200 texenv constant-color register, not per-vertex attributes. When t...

Folding N64 prim/env colors: the sm64 3DS port folds constant combiner colors into the PICA200 texenv constant-color register, not per-vertex attributes. When the combiner has two color inputs, renderTwoColorTris scans the batch, determines which input is constant across all vertices, sets it via C3D_TexEnvColor on texenv stage 0 (update_shader swaps texenv0/1 order as needed) and emits only the non-constant color as the per-vertex color attribute; if neither is constant it falls back lossily to the first vertex's color. This establishes the technique (one texenv write per batch instead of a second attribute) but not a measured gain, and the two-color path is mainly exercised by Goddard/Mario-head combiners in SM64. A claim that the backend's vertex format is fixed at 10 floats with only one color slot, forcing a batch split on every constant-color change, was refuted 0-3 — so a per-vertex prim/env attribute is not ruled out by the precedent.

Evidence: '//determine which color is constant over all vertices for (u32 i = 0; i < buf_vbo_num_tris * 3 && color0Constant && color1Constant; i++) ... update_shader(!color1Constant); C3D_TexEnvColor(C3D_GetTexEnv(0), color1Constant ? firstColor1 : firstColor0);' followed by an emission loop that skips color0 (vtxOffs += hasAlpha ? 4 : 3) when constant and a single C3D_DrawArrays. For F-Zero X's ~30 prim/env changes per crowd frame, the cheaper alternative is to carry prim and env colors as extra per-vertex attributes (PICA200 supports up to 12 vertex attributes and the combiner can take vertex color / secondary color sources) so that consecutive triangles with different constants stay in one draw; verified sources demonstrate only the texenv-constant approach.

Sources: https://github.com/Wyatt-James/sm64-3ds-port/blob/3ds-port/src/pc/gfx/gfx_citro3d.c (renderTwoColorTris lines 656-745, update_shader)

### 7. [high] 30 Hz logic + 60 Hz rendering precedent: the sm64-port 3ds-port 60fps.patch keeps game logic at 30 Hz and reaches 60 Hz by running the full display-list interpr...

30 Hz logic + 60 Hz rendering precedent: the sm64-port 3ds-port 60fps.patch keeps game logic at 30 Hz and reaches 60 Hz by running the full display-list interpreter twice per logic tick — after the normal frame it calls gfx_start_frame(); patch_interpolations(); send_display_list(gGfxSPTask); gfx_end_frame(), re-interpreting the same SPTask with interpolated matrices/vertices patched in place. Interpolation is a fixed midpoint (a+b)/2 between previous and current logic state (stored prevPos/prevAngle/prevScale/prevThrowMatrix/prevFov/prevVertex plus timestamps to skip teleports and camera cuts), not a time-based blend, so the interpolated frame is displayed half a logic step (~16.7 ms of sim time) late. Because there is no render thread (send_display_list is gfx_run on the main thread), this scheme roughly doubles interpreter/dispatch work instead of hiding it — the opposite of what this port needs, where the interpreter, not game logic, is the bottleneck.

Evidence: Patch hunk: 'void produce_one_frame(void) { gfx_start_frame(); game_loop_one_iteration(); ... gfx_end_frame(); + gfx_start_frame(); + patch_interpolations(); + send_display_list(gGfxSPTask); + gfx_end_frame(); }'. math_util.h: '+inline void interpolate_vectors(Vec3f res, Vec3f a, Vec3f b) { res[0] = (a[0] + b[0]) / 2.0f; ... }'; no dt/alpha/frac anywhere in the 2028-line patch. gfx_citro3d.c C3D_FrameRate(30)->60, gfx_3ds.c debounce frames doubled. Last commit touching the patch: 'Fix Patches (#98)' 2024-10-31. Tradeoff for this port: if game logic + bridge pre-pass are already at 30 Hz-affordable cost, the win from decoupling logic is small (game logic is not listed among the top costs), while re-running the interpreter would add ~10+ ms.

Sources: https://github.com/mkst/sm64-port/blob/3ds-port/enhancements/60fps.patch, https://github.com/mkst/sm64-port/blob/3ds-port/src/pc/pc_main.c

### 8. [medium] Ranked recommendations for a locked 60 on New 3DS (expected savings against the ~18.7 ms crowd frame; only the first three are backed by verified primary eviden...

Ranked recommendations for a locked 60 on New 3DS (expected savings against the ~18.7 ms crowd frame; only the first three are backed by verified primary evidence, the rest are inferences from the cost model): (1) Cut batch breaks and SETTILE/state churn in the interpreter — fold prim/env colors into per-vertex attributes or the texenv constant (sm64 precedent), memoize SETTILE into a tile-descriptor cache resolved at draw time, coalesce texrects; targets the 7.8 ms dispatch remainder and 1.2 ms draw submission; expected 2-4 ms; medium risk (combiner correctness), medium effort. (2) Stereo: pack vertices once and issue the right-eye C3D_DrawArrays over the same VBO range after swapping only projection uniform + framebuffer, avoiding sm64's double repack; expected 1-2 ms of the 4.6 ms per-triangle path in stereo mode if the port currently repacks per eye; low risk, low effort. (3) Move the 3.1 ms bridge pre-pass (and/or texture import 0.8 ms, vertex transform 1.2 ms) to a worker thread on core 2, which Luma guarantees is available and otherwise idle; pipeline one display list ahead (one frame of added latency) or split the pre-pass by segment; must be prioritized against the ndsp threads already on core 2 under the strict-priority no-timeslice scheduler; expected up to ~3 ms hidden; medium-high risk (sync, cache coherence on MPCore, latency), high effort; no verified N64-port precedent does this. (4) Core 1 via APT_SetAppCpuTimeLimit (up to 80-89%) for latency-tolerant work such as texture import/decoding; uncertain real throughput because syscore also serves OS threads; low-medium gain. (5) Dispatch micro-architecture (computed goto, hot/cold, Thumb-2 vs ARM, -O3/LTO): sub-millisecond on ARM11 since indirect jumps are unpredicted either way; do last. (6) 30 Hz logic + interpolation: not recommended — the sm64 patch doubles interpreter work and adds half-frame latency.

Evidence: Profile: dispatch remainder 7.8 ms (~130 SETTILE, ~30 prim/env color changes each forcing a batch break), per-triangle 4.6 ms, bridge 3.1 ms, draws 1.2 ms (~22 us each vs 11 register appends in citro3d), GPU ~5.6 ms (not the bottleneck). citro3d shows a texenv color change costs one 5-word write, so the ~30 breaks cost mainly the split (UpdateContext + wrapper + buffer handling); TuxSH: core 2 'is by default completely idle'; sm64 stereo code duplicates the repack loop per eye; ARM11 TRM shows every indirect dispatch jump is 5-9 cycles regardless of style. Magnitudes are estimates, not measurements — no verified source reports measured gains for any of these techniques on 3DS hardware.

Sources: Synthesis of the findings above: Luma3DS PR 1668 / libctru thread.h (core 2 availability), sm64-3ds-port gfx_citro3d.c (stereo double-pack, texenv color folding), citro3d drawArrays.c/base.c/texenv.c (batch cost model), ARM DDI 0301H (dispatch cost), mkst 60fps.patch (interpolation tradeoff)

## Caveats
Verified evidence covers only parts of the research question. Strongly covered: core availability rules (Luma/libctru/3dbrew), the sm64 3DS port's threading and stereo/color-folding/60fps designs, citro3d's state and draw cost model, and ARM11 branch-prediction timings from ARM's TRM. Not covered by any surviving claim: measured numbers for computed-goto vs switch on ARM11, Thumb-2 vs ARM, -O3/LTO/PGO support in devkitARM, __attribute__((hot/cold)), ITCM/DTCM placement, VFPv2 float-to-int/fminf pitfalls, integer/fixed-point clipping, PICA200 per-draw or texenv-change hardware timings, geometry-shader/instancing tricks, single-pass or reduced-resolution stereo techniques (Nintendo or homebrew), and precedents from Daedalus, DS/3DS emulators or other retro ports — those parts of the question remain unanswered and the recommendations for them are inferences from the cost model. The ARM11 numbers come from the ARM1176JZF-S TRM (DDI 0301H); the New 3DS uses the ARM11 MPCore (DDI 0360F), whose predictor description was verified as identical for one claim but the full cycle table could not be re-verified in the MPCore document. The exact core-1 maximum is unresolved: Luma's hbldr sets reslimit 89 while the sm64 code comments '[10-80]' and a claim asserting 80% as the maximum was refuted 0-3. The sm64 stereo and 60fps findings are design-specific to the mkst/Wyatt-James branches (code dated 2023-2026); other forks (e.g. Gericom's) may differ. The CGO 2015 interpreter paper applies to Haswell-class predictors only and must not be used to argue for or against threaded dispatch on ARM11. All expected-savings magnitudes in the ranked list are estimates derived from the port's own profile and the cost model, not published measurements. Web-search budgets were exhausted for several verifications, so contradicting-evidence searches were partial; primary-source (code/TRM) verification was used instead.

## Open questions
- Is there any N64 or retro port on 3DS that actually runs display-list interpretation or draw submission on core 2 (pipelined one frame ahead), and what latency, tearing and synchronization design did it use and what did it measure? The sm64 port only offloads audio.
- Where do the ~22 us per C3D_DrawArrays in this port actually go, given citro3d emits only 11 register writes — UpdateContext texenv/texture binds (including the texture-cache clear), the port's DrawTriangles wrapper, or VBO cache-flush/GX command handling — and can a second DrawArrays over an already-packed range (right eye) be made close to the 11-write floor?
- Can PICA200 render both eyes from one submitted command list (GX command-list re-execution with a different framebuffer and projection uniform patched), or via a geometry shader emitting to two viewports, and has any 3DS homebrew or Nintendo title measured this against brute-force double submission?
- Does devkitARM GCC support -fprofile-generate/-fprofile-use on the 3DS filesystem and how much do PGO/LTO/-O3 and Thumb-2 vs ARM actually change per-command dispatch cost on ARM11 MPCore, and is there a measured comparison of computed-goto vs switch dispatch on ARM11?
